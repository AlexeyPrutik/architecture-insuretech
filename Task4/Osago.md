# Задание 4. Проектирование продажи ОСАГО
![Схема контейнеров С4 предложение](InsureTech_C4_сontainer-diagram-osago.drawio.xml)
Для реализации продажи ОСАГО онлайн было решено создать отдельный сервис **osago-aggregator-app**.

- **Язык/фреймворк:** Kotlin, Spring Boot 3, реактивный с поддержкой корутин.
- **База данных:** PostgreSQL — хранение предложений по заявкам.
- **Кэш / дедупликация:** Redis — хранение ключей `clientId` с TTL 5–10 минут, чтобы не запускать параллельную синхронизацию для одного клиента.
- **Асинхронная обработка:** сервис отправляет запросы к страховым компаниям параллельно, собирает ответы и сохраняет в базу.
- **Отказоустойчивость:** Rate Limiting, Circuit Breaker, Retry, Timeout (60 секунд максимум для страховщиков).
- **Core-app остаётся блокирующим**, потому что переписывать весь существующий сервис на реактивный стек — это большая работа и усложняет поддержку. Вся тяжёлая асинхронная работа забирается на себя **osago-aggregator-app**.

---

## Поток работы

1. Пользователь заполняет заявку на ОСАГО (данные автомобиля, регион, водитель и т.д.) и нажимает **«Получить предложения»**.
2. **Core-app** получает заявку через REST и пересылает её в **osago-aggregator** с `clientId` и данными заявки.
3. **Osago-aggregator**:
  - Проверяет PostgreSQL, есть ли актуальные предложения за последний час.
    - Если есть → возвращает их сразу.
    - Если нет → проверяет Redis ключ `clientId`.
      - Если ключ есть → синхронизация уже идёт → возвращает статус **«Ожидание предложений (процесс может занять до минуты)»**.
      - Если ключа нет → создаёт асинхронный запрос ко всем страховым компаниям (корутины) и ставит ключ в Redis с TTL.
  - Ответы страховщиков сохраняются в PostgreSQL по мере поступления.
4. Пользователь может повторно нажать **«Обновить предложения»** → core-app получает уже готовые предложения из aggregator’а.

---

## Преимущества решения

- Core-app блокирующий → простота поддержки, низкая нагрузка на потоки JVM.
- Асинхронный osago-aggregator → масштабируемый, обрабатывает тысячи пользователей и запросов к страховым.
- Redis предотвращает повторные параллельные синхронизации для одного клиента.
- Полностью соответствует бизнес-требованию: предложения формируются **после заполнения заявки**, пользователь видит либо готовые предложения, либо статус ожидания.
